# Performance Benchmark Results

Generated by `backend/scripts/benchmark.py`, which builds real synthetic
multi-session pcaps (via scapy) and runs them through the actual
`analyze_pcap()` pipeline — not a mock — measuring wall-clock time
(`time.perf_counter`) and peak memory (`tracemalloc`).

**Reproduce this yourself:**
```bash
cd backend
pip install -r requirements-dev.txt
python scripts/benchmark.py
```

## Results

Run on: this dev container (Python 3.12, no GPU, shared/virtualized CPU —
treat absolute numbers as illustrative of *scaling shape*, not a promise
about your hardware).

| Sessions | Packets | Capture size | Time | Peak memory | Packets/sec |
|---|---|---|---|---|---|
| 10  | 110  | 7.0 KB   | 0.44s | 14.7 MB* | 251   |
| 50  | 550  | 35.1 KB  | 0.34s | 0.6 MB   | 1,623 |
| 200 | 2,200 | 140.5 KB | 1.47s | 1.7 MB   | 1,501 |
| 500 | 5,500 | 351.1 KB | 4.22s | 4.2 MB   | 1,302 |

\* The 10-session row's outsized peak-memory reading is one-time import
overhead (numpy/scikit-learn loading lazily on first use in-process), not
a per-session cost — note it doesn't scale up with the later rows despite
those having far more sessions. Peak memory across the rows that matter
(50-500 sessions) stays under 5MB, confirming the streaming `PcapReader`
approach (not loading the whole capture into memory via `rdpcap`) is
doing its job.

## Interpretation

- **Throughput is roughly linear** (~1,300-1,600 packets/sec) across this
  range, with the 10-session row being noise (too small a sample for
  per-packet cost to dominate over fixed overhead).
- **Extrapolating** (linear-scaling assumption, unverified beyond 500
  sessions): a 10,000-packet capture (~1,000 sessions) would be expected
  to take roughly 6-8 seconds — within `ANALYSIS_TIMEOUT_SECONDS`'s
  default 300s budget by a wide margin. A genuinely huge or adversarial
  capture is bounded separately by `MAX_PACKETS_PER_CAPTURE` (default
  500,000), independent of this timing data.
- **This benchmark uses plaintext SMTP sessions only** (cheapest case: no
  TLS record/handshake parsing, no certificate chain validation). A
  capture with heavy TLS/certificate content will run slower per-session
  than these numbers suggest — this benchmark characterizes the
  reconstruction pipeline's scaling, not a worst-case per-session cost.
  If you need a TLS-heavy benchmark, extend `scripts/benchmark.py`'s
  session builder using the pattern in
  `tests/fixtures/_generate_tls_fixture.py`.

## What this does NOT claim

- Not a regression gate — `tests/test_performance_benchmark.py` asserts
  the pipeline *completes* and recovers every session, not that it hits
  these exact numbers (CI hardware varies too much for a tight threshold
  to be meaningful).
- Not measured against a real-world capture with genuinely noisy traffic
  (retransmissions, unrelated protocols mixed in, IP fragmentation) —
  only against clean synthetic sessions, matching what the rest of this
  repo's test corpus uses.
